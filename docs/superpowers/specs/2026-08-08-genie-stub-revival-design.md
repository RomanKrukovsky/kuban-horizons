# Джинния: оживление 18 пустышек

> Дата: 2026-08-08. Источник требований: `GENIE_CONCEPT.md`, `GENIE_VISION.md`.
> Предыдущая спека: `2026-08-07-genie-module-1-design.md` (модуль 1).

## 1. Проблема

Коммит `28dc0f4` («implement deep rules, reality bending mechanics, and 40+
unique Genie systems») добавил 53 файла в пакет `genie`. **18 из них —
фасады**: метод создаёт частицы, отправляет переведённое сообщение и
возвращает `true`, не меняя мир.

Примеры фактического состояния:

| Файл | Заявлено | Фактически |
|---|---|---|
| `MiniaturizationEngine` | сжать регион 100×100 в предмет | `return ItemStack.EMPTY` |
| `LivingPaintingEngine` | войти в измерение картины | частицы + чат, `return true` |
| `BiomeRewriterEngine` | сменить биом, растения, небо, чанкген | только `MagicalSignature.cast` |
| `HybridSpeciesEngine` | «лиса, летающая и светящаяся» | спавнит обычную `EntityTypes.FOX` |
| `WordMaterializer` | материализовать слово буквами | ставит один `GOLD_BLOCK` |
| `GenieMythSystem` | слухи, легенды, праздник | одна строка в чат |

При этом `PROJECT_STATE.md` помечает их `[x]`, а GameTest'ы проходят, потому
что проверяют возвращаемое значение, а не состояние мира: тест
`assertTrue(enterPaintingDimension(...))` проходит на заглушке с
захардкоженным `return true`.

**Цель этой работы:** сделать все 18 механик настоящими и заменить
тесты-обманки на тесты, которые падают при удалении функциональности.

## 4. Ключевое архитектурное решение: один общий фундамент

Пять из 18 механик требуют одного и того же — **сохранить область блоков и
вернуть её обратно**:

- карманные сцены — вернуть мир как было через 60 секунд;
- сжатие мира — положить регион в предмет;
- театр прошлого — восстановить прошлое состояние места;
- гигантизм — сохранить исходник перед увеличением;
- (на будущее) отмена желаний из `GENIE_VISION` — Закон причинности.

Поэтому строится **один модуль `RegionSnapshot`**, а не пять независимых
реализаций. Это единственная точка, где мод пишет и откатывает регионы.

```
genie/world/RegionSnapshot.java     — capture(level, from, to) / restore(level, at)
genie/world/SnapshotStore.java      — хранение снимков (SavedData, SchemaVersion)
registry/KHDataComponents.java      — компонент REGION_PAYLOAD для предмета
```

Контракт `RegionSnapshot`:

- `capture` не меняет мир, возвращает неизменяемый снимок;
- `restore` идемпотентен: повторный вызов даёт тот же результат;
- лимит объёма из конфига (защита от зависания сервера — Закон сохранности);
- при превышении лимита — отказ с сообщением, а не молчаливое усечение.

Потребители зависят только от этих двух методов и ничего не знают про NBT.

## 5. Группы работы

Всего в группах 20 механик: 18 фасадов из раздела 1 плюс две **частично
реализованные** — `GigantismScaleEngine` и `FlyingStructureEngine`. Они не
были фасадами (в них есть работающая логика), но заявленную в концепте
глубину не покрывают, а зависят от того же `RegionSnapshot`, поэтому
доделываются в одном срезе.

### Группа 1 — фундамент
`RegionSnapshot`, `SnapshotStore`, `KHDataComponents.REGION_PAYLOAD`,
серверный конфиг лимитов. Без UI-эффектов.

### Группа 2 — реальные изменения мира (6)
| Механика | Что значит «по-настоящему» |
|---|---|
| `MiniaturizationEngine` | регион исчезает из мира и живёт в предмете; разворот восстанавливает блок-в-блок |
| `PocketSceneEngine` | сцена строится из шаблона, по таймеру мир возвращается в исходное состояние |
| `WordMaterializer` | шрифт 5×5, каждая буква — блоки; «золото» → золотые блоки, «дождь» → начинается дождь |
| `MagicDrawingHandler` | ломаная по точкам игрока превращается в связную структуру (мост/арка) |
| `GigantismScaleEngine` | увеличение сущности через атрибут масштаба + пропорции коллизии |
| `FlyingStructureEngine` | структура отрывается и следует за игроком, оставаясь связной |

### Группа 3 — память и характер (5)
`ItemMemoryReader` (реальная история из компонентов и памяти мира),
`BlockWhispersEngine` (структуры/колокол/портал со записями из
`WorldGenieMemory`), `NPCPersonalityEngine` (настоящие атрибуты и `Brain`,
персистентно), `WishContractEngine` (реальная книга: условия, мелкий шрифт,
лазейка, срок), `GenieDreamEngine` (сцена сна с символами будущих событий).

### Группа 4 — живой мир (4)
`HybridSpeciesEngine` (свойства реально применяются: полёт, свечение,
наследование потомству), `VisualReenactmentEngine` (призрачные NPC
воспроизводят записанные события места), `GenieMythSystem` (слухи,
искажение фактов со временем, ежегодный праздник), `OwnerDeathProtocol`
(четыре реальных варианта из концепта, не сообщение).

### Группа 5 — сложные (4)
`LivingPaintingEngine` (настоящее измерение через `LevelStem` +
`FlatLevelSource`, вход и возврат; сюда же зеркальный мир),
`BiomeRewriterEngine` (смена биома с растительностью и небом),
`GenieRoleSwap` (обмен ролями: игрок в лампе, джинния свободна) и
`TrueOmnipotenceEnding` (финал Желания №1 со снятием HUD).

### Группа 6 — сцена трансформации (1)
`DistortedWishEngine` — особый случай: он делегирует в
`PlayerGenieTransformationController`, который **делает реальную работу**
(меняет attachment, выдаёт полёт, снимает смертность). Дефект другой: все
пять стадий выполняются мгновенно в одном тике, вызывая друг друга
каскадом (`startTransformation` → `advanceToStage2` → `advanceToStage3And4`).

Концепт же описывает кинематографичную сцену: сердечки исчезают по одному,
ноги растворяются снизу вверх, управление временно отключается, камера
переключается в третье лицо, и только потом появляется скелет для проверки
неуязвимости.

Задача: превратить мгновенный каскад в **пошаговую сцену по тикам** с
сохранением стадии в attachment (чтобы переживала выход из игры), не меняя
уже работающую логику самих стадий.

## 6. Вне объёма этой работы

Явно НЕ делаем, чтобы не создавать новых пустышек:

- **неевклидова геометрия** (снаружи 5 блоков, внутри 500) — отдельное
  исследование;
- **альтернативные таймлайны** («А что если?») — требует форка состояния мира;
- **мета-желания, меняющие правила симуляции** — уже частично есть в
  `MetaRuleEngine`, отдельный срез;
- **proposal/risk/confirmation pipeline** — следующий обязательный срез из
  `PROJECT_STATE.md`, эта работа его не подменяет.

Эти пункты остаются в `GENIE_VISION.md` как незакрытые и **не помечаются
готовыми**.

## 7. Тестирование

Причина, по которой прошлая попытка прошла тесты: проверялось возвращаемое
значение. Новое правило — **тест обязан падать при удалении реализации**.

| Механика | Проверка состояния мира |
|---|---|
| Снимок/восстановление | случайный регион → снимок → залить камнем → restore → сверить каждый блок |
| Миниатюризация | после сжатия блоков нет; после разворота — идентичны исходным |
| Карманная сцена | во время сцены блоки есть; после таймера мир равен исходному |
| Буквы | «золото» ставит именно золотые блоки в форме букв, а не один блок |
| Гибрид | сущность реально имеет полёт и свечение, а не является обычной лисой |
| Измерение | игрок оказался в другом `ServerLevel`; возврат вернул в исходный |
| Биом | биом в позиции изменился на запрошенный |
| Контракт | книга содержит условие, срок и лазейку |
| Трансформация | стадии идут по тикам, а не все в одном; стадия переживает перезаход |

Дополнительно: аудит-тест, который сканирует пакет `genie` на признаки
фасада (`return ItemStack.EMPTY`, `return true` без изменения мира) и не
даёт вернуть заглушки.

## 8. Правки документации

Ложные `[x]` — часть дефекта. В рамках работы:

- `PROJECT_STATE.md` — статус по факту, для нереализованного `[ ]`;
- `GENIE_VISION.md` — матрица «работает / частично / не начато»;
- `TEST_PLAN.md` — правило «тест обязан падать без реализации»;
- `CHANGELOG.md` — запись о замене фасадов на реализации.
