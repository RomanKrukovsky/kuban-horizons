# Архитектура Kuban Horizons

Документ фиксирует техническую архитектуру мода и все значимые
архитектурные решения (AD-xxx). Изменение зафиксированного решения требует
новой записи с обоснованием.

## 1. Платформа

| Параметр | Значение |
|----------|----------|
| Minecraft | Java Edition **26.2** |
| Mod loader | **NeoForge 26.2.0.48-beta** (линейка 26.2) |
| Java (сборка и рантайм) | **25** (toolchain через foojay-resolver) |
| Система сборки | Gradle 9.2.1 (wrapper) + ModDevGradle 2.0.143 |
| Mod ID | `kubanhorizons` |
| Корневой пакет | `dev.romankrukovsky.kubanhorizons` |

### Архитектурные решения

**AD-001. Версия Minecraft: 26.2.**
Спецификация проекта в шапке требует «Minecraft Java Edition 1.26.2 (!!!)»,
а в разделе «Первые действия» упоминает 1.21.1. Это противоречие. Начиная
с 2025 года Mojang перешла на календарную нумерацию: актуальная версия
игры называется **26.2** (линейка «1.26.x» в старой нотации). Тройное
восклицание в шапке трактуем как приоритет: целевая версия — 26.2.
NeoForge для 26.2 существует (26.2.0.48-beta, официальный MDK
`MDK-26.2-ModDevGradle`). Версия 1.21.1 в разделе 4 — устаревший фрагмент
шаблона промпта. Решение: **Minecraft 26.2 + NeoForge 26.2.0.48-beta**.
Обновление на стабильный NeoForge 26.2.x выполняется в рамках патч-версий
без изменения этого решения.

**AD-002. Java 25 вместо Java 21.**
Спецификация называет Java 21, но Minecraft 26.2 поставляется игрокам с
Java 25, и официальный MDK для 26.2 требует toolchain Java 25. Собирать мод
под Java 21 для этой версии игры технически невозможно. Решение: **Java 25**
(байткод и toolchain), исходный код пишем без preview-фич. Отклонение от
спецификации зафиксировано здесь как обязательная запись.

**AD-003. ModDevGradle, а не NeoGradle.**
ModDevGradle — рекомендованный NeoForged плагин с более быстрой настройкой
и стабильным datagen/run-конфигурированием. Шаблон: MDK-26.2-ModDevGradle
(CC0).

**AD-004. Русскоязычные комментарии и документация.**
Основной язык разработки — русский (по спецификации). Идентификаторы кода —
английские, комментарии и Javadoc — русские. Сообщения коммитов — английские
по формату Conventional Commits (по разделу 20 спецификации).

**AD-005. Datagen как единственный источник JSON-данных.**
Все blockstates, модели (кроме сложных ручных), рецепты, loot tables, теги,
языковые файлы, advancements и worldgen-данные генерируются datagen.
Ручные JSON допускаются только для уникальных нестандартных моделей и
шаблонов структур. Сгенерированные файлы коммитятся в
`src/generated/resources` для воспроизводимости и работы CI.

**AD-006. Версионирование данных сохранений.**
Каждый сохраняемый компонент (block entity, saved data, attachments)
содержит поле `SchemaVersion`. Миграции — только вперёд, с сохранением
неизвестных полей. Registry ID после публичного релиза не переименовываются.

## 2. Структура пакетов

```
dev.romankrukovsky.kubanhorizons
├── KubanHorizons            — главный класс: подключение регистраций
├── registry                 — раздельные регистрационные классы:
│   ├── KHBlocks             — блоки
│   ├── KHItems              — предметы
│   ├── KHBlockEntities      — block entities
│   ├── KHMenus              — контейнеры/меню
│   ├── KHRecipes            — типы и сериализаторы рецептов
│   ├── KHSounds             — звуковые события
│   ├── KHParticles          — частицы
│   ├── KHCreativeTabs       — вкладки творческого режима
│   ├── KHDataComponents     — компоненты данных предметов
│   ├── KHEntities           — сущности
│   └── KHFoods              — свойства еды (константы)
├── block                    — классы блоков
├── blockentity              — логика block entities
├── item                     — классы предметов
├── entity                   — сущности и их AI
├── worldgen                 — общая генерация мира
├── biome                    — биомы и модификаторы
├── structure                — структуры и процедурная застройка
├── crop                     — сельскохозяйственные культуры
├── soil                     — система плодородия
├── irrigation               — система орошения
├── food                     — еда и пищевые цепочки
├── processing               — перерабатывающие устройства (общая логика)
├── trade                    — профессии и торговля
├── network                  — сетевые пакеты (payloads)
├── client                   — client-only входная точка
│   ├── render               — рендереры
│   ├── screen               — экраны GUI
│   └── particle             — клиентские частицы
├── sound                    — звуковая логика
├── advancement              — триггеры достижений
├── datagen                  — все datagen-провайдеры
├── config                   — серверная и клиентская конфигурация
├── compat                   — интеграции (JEI, Jade, FD, Create…) — по пакету на мод
├── gametest                 — автоматические игровые тесты
└── util                     — утилиты
```

Правила:

- **Запрещён** один гигантский класс регистрации: каждый тип реестра — свой
  класс в `registry`.
- **Client/Server-разделение**: классы из `client.*` никогда не загружаются
  на dedicated server. Входная точка клиента отмечена `@Mod(dist = Dist.CLIENT)`.
  Проверка — запуск `runServer` в CI-плане тестирования.
- Пакет `compat.<modid>` загружается только при наличии соответствующего
  мода (`ModList.get().isLoaded(...)`), классы интеграции не упоминаются
  в общем коде напрямую.
- `gametest` — тестовый код; не содержит игровой логики.

## 3. Потоки данных и синхронизация

- Источник истины — сервер. Клиентские данные никогда не принимаются на веру.
- Синхронизация block entities — через `getUpdateTag`/`onDataPacket` и
  меню-`ContainerData` для GUI-прогресса; полные custom payloads — только
  когда стандартных механизмов недостаточно.
- Пакеты регистрируются в `network` с версионированием протокола.
- Никакой отправки пакетов на каждый tick: только при изменении данных,
  с дребезг-защитой (change detection).

## 4. Производительность (принципы)

- Никакого сканирования чанков или сетей орошения каждый tick: сети
  кэшируются как графы и перестраиваются событийно (при изменении блоков).
- Логика роста культур — через стандартный `randomTick`, без собственных
  scheduler-циклов на каждое растение.
- Плодородие хранится per-chunk (data attachments), а не per-block-tick.
- Block entities — только там, где есть инвентарь/прогресс/уникальное
  состояние.
- Бюджеты: см. TECH_SPEC.md и PERFORMANCE.md (появится на этапе полировки).

## 5. Конфигурация

- `config/KHServerConfig` — SERVER-тип: частоты биомов/структур, скорость
  роста, сложность плодородия, эффективность орошения, торговля,
  выключатели подсистем.
- `config/KHClientConfig` — CLIENT-тип: частицы, громкость атмосферы,
  визуальные эффекты, подсказки, режим отладки.
- Все значения валидируются диапазонами `ModConfigSpec`; некорректный
  ввод откатывается к значению по умолчанию, а не роняет игру.

## 6. Тестирование

- GameTest-инфраструктура в `gametest`; каждая законченная механика имеет
  тест. Запуск: `./gradlew runGameTestServer` и в CI.
- Полный список проверок — TEST_PLAN.md.

## 7. CI

GitHub Actions (`.github/workflows/build.yml`): сборка + datagen-чистота +
GameTest на каждый push/PR в `main` и рабочие ветки.
