## 4. Wish Capability Kernel

### 4.1 Назначение

`Wish Capability Kernel` является общим серверным слоем, который превращает абстрактные желания джиннии в строго типизированные, проверяемые и транзакционно исполняемые операции.

Он не является:

* command executor;
* scripting engine;
* Java interpreter;
* raw NBT editor;
* WorldEdit wrapper;
* LLM tool proxy.

Он является закрытым registry проверенных возможностей мира.

Общий поток:

```text
Natural Language Wish
        ↓
GeniePlanner
        ↓
Untrusted OperationPlan
        ↓
PlanGate
        ↓
ValidatedWishPlan
        ↓
Wish Capability Kernel
        ↓
resolve targets
        ↓
assess effects
        ↓
build preview
        ↓
authorization / consent
        ↓
transaction
        ↓
world adapters
        ↓
verification
        ↓
audit + undo
```

Это сохраняет фундаментальную границу существующей архитектуры: сервер владеет полномочиями и исполнением, а Genie — намерением и планированием.

---

# 4.2 CapabilityId

Каждая возможность имеет стабильный versioned ID.

```java
record CapabilityId(
    String namespace,
    String name,
    int version
) {}
```

Примеры:

```text
genie:item.create@1
genie:structure.place@1
genie:terrain.transform@1
genie:entity.transform@1
genie:weather.set@1
genie:time.set@1
genie:teleport.safe@1
genie:player.transformGenie@1
genie:region.restore@1
genie:pocketRealm.create@1
genie:rule.localGravity@1
```

Версия является частью identity.

Изменение semantic behavior требует новой версии.

Например:

```text
genie:terrain.transform@1
```

не может незаметно получить другую модель rollback в будущем.

# 4.5 Capability execution contract

Каждая capability должна реализовывать одинаковый lifecycle:

```java
interface WishCapability<A, R> {

    CapabilityDescriptor descriptor();

    Resolution<A> resolve(
        WishExecutionContext context,
        A args
    );

    CapabilityAssessment assess(
        WishExecutionContext context,
        Resolution<A> resolution
    );

    CapabilityPreview preview(
        WishExecutionContext context,
        Resolution<A> resolution
    );

    R execute(
        ConfirmedCapabilityRequest<A> request
    );

    CapabilityVerification verify(
        CapabilityExecutionReceipt receipt
    );
}
```

LLM никогда не вызывает `execute()`.

# 4.6 Строгая типизация arguments

Пример capability:

```text
genie:weather.set@1
```

Args:

```java
record SetWeatherArgs(
    DimensionSelector dimension,
    WeatherType weather,
    int durationTicks
) {}
```

Не допускается:

```json
{
  "command": "/weather thunder"
}
```

Допускается только:

```json
{
  "dimension": {
    "type": "CURRENT"
  },
  "weather": "THUNDER",
  "durationTicks": 6000
}
```

---

# 4.7 Unknown fields

Неизвестные поля отклоняются.

Если schema ожидает:

```json
{
  "weather": "...",
  "durationTicks": 0
}
```

то:

```json
{
  "weather": "RAIN",
  "durationTicks": 6000,
  "forceAdmin": true
}
```

является invalid plan.

Никакого permissive parsing.

# 4.8 Target selectors

Главная задача Kernel — не позволять LLM передавать произвольные raw object references.

Используются typed selectors.

```java
sealed interface WishTargetSelector {}
```

Категории:

```text
BlockSelector
RegionSelector
EntitySelector
PlayerSelector
StructureSelector
DimensionSelector
ItemSelector
SnapshotSelector
RealmSelector
```

# 4.9 BlockSelector

```java
sealed interface BlockSelector {

    record LookTarget(
        double maxDistance
    ) implements BlockSelector {}

    record Exact(
        GlobalBlockPos position
    ) implements BlockSelector {}

    record Relative(
        BlockPos offset
    ) implements BlockSelector {}
}
```

`Exact` не означает безусловное доверие.

Сервер всё равно проверяет:

* dimension;
* world bounds;
* permission;
* loaded state;
* allowed footprint.

# 4.10 RegionSelector

```java
sealed interface RegionSelector {

    record CurrentSelection(

    ) implements RegionSelector {}

    record RadiusAroundBlock(
        GlobalBlockPos center,
        int radius
```

Это продолжает существующее правило, согласно которому клиент не может передать готовый AABB без серверной проверки.

# 4.12 PlayerSelector

Игроки требуют отдельной категории.


# 4.13 Consent boundary

Любое желание, затрагивающее другого player actor, проходит через consent policy.

Пример:

```text
"Преврати Васю в джиннию."
```

не должно автоматически исполняться.

Получатель получает:

```text
Игрок Roman хочет применить к вам:

GENIE TRANSFORMATION

Изменения:
- физическое бессмертие;
- новая форма;
- natural flight;
- vessel binding;
- изменение death mechanics.

[Принять]
[Отклонить]
```

# 4.16 Risk classification

Предлагается пять уровней:

```text
R0 — READ_ONLY
R1 — COSMETIC
R2 — LOCAL_REVERSIBLE
R3 — STRONG_REVERSIBLE
R4 — WORLD_CRITICAL
R5 — REALITY_CRITICAL
```

---

# 4.17 R0 — READ_ONLY

Примеры:

* inspect snapshot;
* inspect structure;
* inspect entity;
* query biome;
* measure region;
* preview wish.

Подтверждение не требуется.

---

# 4.18 R1 — COSMETIC

Примеры:

* particles;
* temporary illusion;
* visual disguise;
* non-persistent aura.

Обычно не требуется durable transaction.

---

# 4.19 R2 — LOCAL_REVERSIBLE

Примеры:

* создать несколько предметов;
* изменить погоду;
* безопасно телепортировать одного игрока;
* временно изменить внешний вид.

Preview может быть компактным.

---

# 4.20 R3 — STRONG_REVERSIBLE

Примеры:

* построить дом;
* трансформировать участок земли;
* изменить biome региона;
* переместить structure;
* массово изменить entities.

Требуется:

```text
preview
confirmation
before-image
transaction
verification
undo
```

---

# 4.21 R4 — WORLD_CRITICAL

Примеры:

* изменить крупный регион;
* восстановить значительный snapshot;
* создать pocket realm;
* изменить persistent entity population;
* массово изменить settlement.

Требуется:

* expanded preview;
* disk estimate;
* chunk estimate;
* explicit consent;
* strict quota;
* retained undo;
* recovery gate.

---

# 4.22 R5 — REALITY_CRITICAL

Примеры:

* изменить фундаментальное local world rule;
* genie transformation;
* alter mortality model;
* change local gravity;
* permanent dimension rule;
* large temporal restore;
* irreversible transformation.

R5 operation нельзя исполнять одной natural-language репликой.

Обязательно:

```text
interpretation
↓
preview
↓
explicit confirmation
↓
durable transaction
↓
verification
```

---

# 4.25 Preview

# 4.28 Confirmation binding

Подтверждение связано с:

* capability ID;
* planner intent;
* resolved targets;
* preview digest;
* compatibility report;
* player UUID;
* consent set;
* expiry.

Это расширяет уже существующий принцип single-use confirmation, связанного с точным preview и состоянием мира.

# 4.29 Stale preview

Если после preview:

* кто-то изменил регион;
* target entity исчез;
* player сменил dimension;
* structure была перестроена;
* изменился mod registry;
* изменился consent;

preview становится:

```text
STALE
```

Исполнение запрещено.

Нужно новое preview.

---

# 4.30 Primitive execution model

Capability не обязана быть одной низкоуровневой операцией.

Например:

```text
structure.place
```

внутри может выполнять:

```text
reserve chunks
capture before-image
prepare blocks
prepare block entities
remove replaceable entities
stage structure blocks
reconcile lighting
reconcile heightmaps
verify
```

Но это скрытая реализация capability.

Planner не должен видеть эти внутренние steps.

---

# 4.31 Почему не давать planner низкоуровневые block.set

Запрещается делать основной API вида:

```text
block.set
block.set
block.set
block.set
...
```

для крупных желаний.

Причины:

* огромные plans;
* дорогая LLM генерация;
* сложный validation;
* риск неполной операции;
* плохая rollback semantics;
* низкая производительность;
* невозможность разумного compatibility анализа.

Planner должен описывать намерение.

Runtime — реализацию.

# 4.52 Запрет скрытых world mutations

Capability descriptor обязан объявлять все mutation domains.

Если capability объявила:

```text
mutatesBlocks = true
mutatesEntities = false
```

но execution пытается изменить entity domain:

```text
verification failure
→ rollback
→ capability quarantined
```

---

# 4.53 Capability quarantine

Если capability:

* нарушила declared effects;
* не прошла verification;
* вызвала inconsistent rollback;
* обнаружила unsupported state;

она может быть автоматически отключена:

```text
CapabilityState = QUARANTINED
```

до следующего restart/admin review.

# 4.98 Fault injection

Для каждого strong mutation тестируется crash:

```text
before PREPARED
after PREPARED
mid APPLYING
before VERIFYING
mid VERIFYING
during ROLLBACK
after COMMITTED before audit publication
```

После restart состояние должно быть доказуемо:

```text
BEFORE
```

или:

```text
AFTER
```

но никогда:

```text
HALF_APPLIED
```

Это соответствует ключевой гарантии уже выбранного ядра: после сбоя мир должен находиться либо полностью в состоянии «до», либо полностью в подтверждённом состоянии «после».

## 5. Следующий слой — Genie Transformation & Morphology Runtime

После Wish Capability Kernel отдельный модуль должен формально реализовать превращение игрока в джиннию.

Он должен включать:

* transactional transformation;
* смену player model;
* true form;
* human disguise;
* отсутствие ног в true form;
* procedural magical tail;
* natural flight controller;
* physical immortality;
* avatar destruction/remanifestation;
* size shifting;
* shapeshifting;
* custom animation graph;
* secondary animation;
* vessel birth;
* multiplayer synchronization;
* persistence;
* death interception;
* Void handling;
* compatibility с armour/cosmetics;
* camera system;
* first-person true-form rendering;
* переход назад в смертную форму, если сюжет допускает это.

Отдельно необходимо определить `GeniePlayerBridge`, потому что превращённая джинния остаётся `ServerPlayer` для Minecraft networking и permissions, но одновременно получает `GenieIdentity` и supernatural runtime.

Это позволит избежать попытки заменить реального player entity кастомным mob entity и существенно упростит совместимость с vanilla multiplayer, inventories, advancements, permissions и сторонними модами.
